# 特勤处子弹 A/D 重置与完成识别诊断设计

## 背景

当前子弹目标定位通过“向上滚 50 次置顶，再向下滚配置次数”实现。实机确认应改为每个目标先按 `A`、再按 `D` 重置列表状态，随后只向下滚配置次数。

`ammo.success` 另有环境差异：同一配置在 runtime 中连续采样约为 `0.6001`，手动校准测试为 `1.0000`，阈值为 `0.7500`。手动测试直接截图；runtime 会先恢复并聚焦游戏，且运行期间存在置顶 operation window。现有证据只能确认采样画面不同，不能据此降低阈值或判定模板失效。

## 方案裁决

采用最小根因方案：

1. 子弹定位只替换重置动作，复用现有逐次滚轮、可取消等待、点击与鼠标停放能力。
2. 校准测试增加与 runtime 一致的游戏前台和鼠标停放条件。
3. runtime 识别超时时保存最后一次实际识别区域截图，错误信息携带截图路径和最后采样分数。
4. 不降低 `ammo.success` 阈值，不增加无限重试，不改当天成功/失败状态机。

未采用方案：

- 仅延长识别 timeout：稳定低分不会因等待变成命中，只延长卡住时间。
- 直接降低阈值：`0.6001` 与手测 `1.0000` 差距过大，降低阈值会扩大误判范围。
- 每种子弹保存独立成功模板：当前问题尚未证明来自子弹类型差异，先保留全局 `ammo.success`。

## 子弹目标定位状态机

每个启用目标独立执行以下连续操作块，整个操作块仅发布一次键鼠倒计时：

1. 恢复并聚焦游戏窗口。
2. 发送一次 `A` 按键点击。
3. 可取消等待 `100ms`。
4. 发送一次 `D` 按键点击。
5. 可取消等待 `100ms`。
6. `scrollSteps > 0` 时，把鼠标移至目标点击区域，逐次向下滚 `scrollSteps` 次；相邻滚轮事件间隔 `100ms`。
7. 无论 `scrollSteps` 是否为 `0`，均可取消等待 `1000ms`，让列表完成切换或滚动。
8. 点击目标区域。
9. 把鼠标移至 `runtime.mouseParking`，进入既有 `ammo.success / ammo.exchange / ammo.fill` 识别流程。

删除所有向上滚轮。`scrollSteps` 继续保存非负整数，但 UI 文案改为“A/D 重置后向下滚动次数（0 表示不滚动）”。旧配置数值原样保留，无 schema 迁移。

紧急停止在 A 后触发时不得发送 D；在 D 后触发时不得滚轮；在滚轮或稳定等待期间触发时不得点击目标。停止后沿用现有输入释放和账号状态处理。

## run 级键鼠倒计时

倒计时按整个特勤处 run 计数，不按账号、登录、导航、制作或子弹子流程重置：

1. 每次新 run 首个键鼠操作块显示 `5 → 4 → 3 → 2 → 1`，即使该动作此前按固定流程不显示倒计时。
2. 同一 run 后续每个此前需要倒计时的键鼠操作块只显示 `1`。
3. 多账号 round 只在第一个账号首次键鼠操作前显示 5 秒；后续账号全部使用 1 秒。
4. 单账号登录、导航、制作、子弹试运行分别属于独立 run，各自首次倒计时为 5 秒。
5. 首个键鼠块之后，登录账号列表接管期间和固定制作探测段原本不重复提示的输入继续不提示。
6. 导航和制作的用户可配置固定等待、A/D 的 `100ms` 间隔、滚轮的 `100ms` 间隔、滚动后的 `1000ms` 稳定等待，以及校准测试的 3 秒准备时间均不属于键鼠提示倒计时，不作修改。

run 创建时初始化“首次键鼠块尚未执行”。每个键鼠块原子请求时长：首次请求返回 5；后续原本需要倒计时的块返回 1；后续原本不提示的块返回空值。紧急停止期间不得继续倒计时或进入输入。

## `ammo.success` 同环境校准测试

游戏内 template 目标的“测试”流程调整为：

1. 保存当前草稿并读取冻结后的目标区域、参考图、阈值、游戏可执行路径和 `runtime.mouseParking`。
2. 给用户 3 秒切换准备时间。
3. 恢复并聚焦游戏窗口。
4. 把鼠标移至 `runtime.mouseParking`。
5. 按现有规则间隔约 `400ms` 双采样。
6. 显示两次分数并按原阈值保存校准验证状态。

该流程不点击游戏 UI，不发送 A/D，不启动兑换，不创建当天成功或失败状态。WeGame 目标仍使用现有手动测试流程，避免错误聚焦游戏。

目标分类按 key 前缀处理：`game.*`、`craft.*`、`ammo.*` 使用游戏前台测试；`wegame.*` 保持现状。若游戏路径、游戏窗口或鼠标停放点缺失，直接返回明确错误，不盲目采样桌面。

## 运行时失败截图

`ammo.success` 在 30 秒内未连续命中时，重新截取一次冻结区域并保存 PNG：

```text
<应用数据目录>/special_ops_diagnostics/<时间戳>-<账号QQ>-ammo.success.png
```

错误记录包含：目标 key、阈值、最后双采样、截图绝对路径。截图失败不能覆盖原识别错误；只附加“诊断截图保存失败”。诊断图只截取用户已配置的 `ammo.success` 区域，不截全屏，不包含 WeGame 账号或密码区域。

诊断图用于比较 runtime 与校准测试画面。若同环境测试也降至约 `0.6001`，说明前台/hover/动画状态改变了像素，应由用户在该状态重新上传参考图；若同环境测试保持 `1.0000`，再对比 runtime 诊断图定位 operation window 覆盖或兑换状态差异。

## 代码边界

- `input_simulation.rs`：增加复用现有单键与取消语义的字母按键入口；不新建输入框架。
- `special_ops/mod.rs`：`ProductionAmmoDriver::position_and_click` 编排 A/D、等待、下滚和点击；校准测试按目标前缀选择采样环境；runtime timeout 接入诊断截图保存。
- `special_ops-page.tsx`：只改滚动次数字段文案和游戏内模板测试提示。
- `template_observer.rs`：保留匹配算法和阈值；仅在需要时暴露最后截图所需的最小 capture 能力。
- 持久化 schema、Tauri command 名、账号/轮次状态机不变。

## 测试

### Rust

- `scrollSteps = 0`：事件顺序为 `A → 100ms → D → 100ms → 1000ms → click`，无滚轮。
- `scrollSteps > 0`：A/D 后仅逐次向下滚配置次数，间隔 `100ms`，结束等待 `1000ms`。
- 每个目标重新执行 A/D，不继承前一目标位置。
- 在 A、D、滚轮、稳定等待各阶段取消时，后续输入不再发送。
- 新 run 首次倒计时返回 5 秒，后续返回 1 秒。
- 同一多账号 round 切换账号后仍返回 1 秒；新建 run 后恢复为 5 秒。
- 单独导航与单独制作试运行的首个固定动作也显示 5 秒；其后固定动作仍不提示。
- 游戏内校准测试先聚焦并停放鼠标；WeGame 校准测试不聚焦游戏。
- `ammo.success` timeout 保存区域截图；保存失败保留原 timeout。

### 前端

- 页面显示“A/D 重置后向下滚动次数（0 表示不滚动）”。
- 测试中状态与错误仍回到现有校准结果区域，不新增 modal。

## 实机验收

1. 目标滚动次数 `0`：观察每个目标均执行 A、D，等待后直接点击。
2. 目标滚动次数大于 `0`：观察无向上滚，向下次数完整且不丢步。
3. A/D 或滚动期间触发紧急停止：后续输入立即终止。
4. 在与 runtime 相同兑换完成画面测试 `ammo.success`：记录双采样分数。
5. 再跑一次单账号兑换试运行。若仍超时，读取错误中的诊断图路径并与参考图对比后再裁决根因。
