# 制作识别超时与停止竞态设计

## 背景

单账号制作试运行存在三类独立问题，组合后表现为整个特勤处页面无法继续操作：

1. 制作成功持久化在 `SettingsCoordinator::with_runtime_change` closure 内再次调用 `current_revision()`，同一线程重复获取非递归 revision 锁，形成确定性死锁。
2. 制作模板等待没有业务超时。参考图、区域或界面状态不匹配时，worker 会永久轮询。
3. 普通取消先把 snapshot 标为 `stopped` 并返回，但 worker、持久化和窗口/热键资源尚未完成清理。前端据此提前开放校准测试和保存，产生并发竞争。

附带问题：

- `craft.abort` 连续调用两次标准双采样，实际要求四次命中。
- 点击动作完成后未发布下一识别阶段文案，状态窗长期保留“正在执行游戏点击”。
- 制作台点击点可误校准到另一制作台，当前预检无法发现。

## 目标

- 消除制作成功持久化的自锁。
- 所有制作识别等待必须有界，任何模板错误都不能永久占用 runtime。
- 明确区分“停止已请求”和“清理已完成”。
- active run 存在期间禁止校准、模板测试、设置保存和启动新试运行。
- 失败结果显示真实步骤、目标 key 和最后两次 similarity。
- 阻止明显跨制作台的点击点误校准。

## 非目标

- 不重写全局 `SettingsCoordinator`。
- 不把全部工具迁移到 actor queue。
- 不实现多账号 round、四制作台批处理或子弹兑换。
- 不修改模板匹配算法和阈值含义。
- 不通过静默缩放修正错误坐标。

## 方案

### 1. 持久化边界

`with_runtime_change` closure 只负责：

1. 克隆当前 special-ops settings。
2. 修改副本并写入 `special_ops_settings.json`。
3. 写入成功后替换内存 settings，并返回更新后的副本。

closure 返回后，调用方使用 `with_runtime_change` 返回的 revision 构建 bootstrap 并发送事件。禁止在任何 `with_revision`、`with_runtime_change` 或 `with_profile_change` closure 内调用 `current_revision()`。

制作成功、制作取消后标记不确定状态均采用同一结构：

```text
with_runtime_change(修改并保存) -> (settings, revision)
                                  -> emit_state(settings, revision)
                                  -> runtime cleanup
```

该约束增加到代码注释和回归测试，避免后续 round executor 重复引入自锁。

### 2. 有界识别等待

在 `template_observer` 增加带 deadline 的双采样等待接口。制作 runtime 不再直接调用无界 `wait_for_target_match` 或 `wait_for_any_consistent_match`。

- 单个制作步骤默认最长等待 30 秒。
- 取消 flag 每 50ms 继续检查；取消优先于超时。
- 每轮仍保持约 400ms 双采样间隔。
- 超时返回目标 key、threshold、最后两次 similarity。
- 初始制作台状态继续只采样一轮：同时未命中“可收取”和“空闲中”时直接结束并提示，不进入 30 秒等待。

30 秒是制作页面状态切换的容错上限，不作为成功条件。识别成功仍必须来自连续两次模板命中。

### 3. 中止确认

`craft.abort` 只调用一次标准双采样等待。两次 similarity 均达到 threshold 后，以第二次截图完成时刻作为实际开始时间；随后计算并保存下一次完成时间。

不再要求两组双采样，不读取游戏 UI 展示的制作时长。

### 4. 准确阶段提示

每次动作结束、进入识别等待前发布具体文案：

- `正在确认奖励页面`
- `正在确认<制作台>已空闲`
- `正在确认<制作台>制作列表已打开`
- `正在确认配方已选中`
- `正在确认生产或一键补齐按钮`
- `正在确认制作已开始`

超时或取消后，最终 snapshot 使用真实失败步骤，不保留上一条点击文案。

### 5. 停止状态与资源所有权

增加运行状态 `stopping`，语义为取消 flag 已设置、输入已停止，但 worker 尚未完成持久化和资源清理。

普通取消：

1. 设置取消 flag。
2. snapshot 进入 `stopping`。
3. command 立即返回“正在取消制作试运行”。
4. worker 从识别/输入边界退出。
5. 若已执行键鼠输入，按既有规则标记制作台状态不确定。
6. worker 保存结果、释放热键和运行窗口，再发布最终 `stopped` 并清空 active run。

紧急停止：

1. 立即设置取消 flag并调用输入释放。
2. snapshot 进入 `stopping`。
3. 不在 command 线程等待 `SettingsCoordinator`。
4. worker 负责持久化不确定状态和最终资源清理。

停止 command 只登记停止请求，不再与 worker 竞争同一次持久化。资源只由最终收尾路径释放一次。

### 6. 运行门禁

前端以“`runSnapshot` 仍存在”为 active run 判断依据，不再把 `stopped` 事件直接视为资源已清理。

active run 期间禁用：

- 登录、导航、制作试运行启动按钮。
- 普通设置编辑和保存。
- 参考图上传、清除、模板测试。
- 点击点/识别区域框选。

后端对下列 command 增加同样门禁并快速返回错误，不能只依赖前端：

- `special_ops_save_settings`
- `special_ops_test_calibration_target`
- calibration begin/submit/cancel commands
- 三类试运行 start commands

启动试运行前仍先 flush 已排队设置；启动成功后不再产生 autosave。

### 7. 制作台点击点一致性预检

四个制作台各自建立由 `craft.claimReady.<station>` 与 `craft.idle.<station>` 组成的状态区域包络。

提交 `craft.station.<station>` 点击点时：

- 若自己的状态区域尚未配置，不执行空间校验。
- 若点击点落入另一制作台包络、且不落入自己的包络，拒绝保存并指出疑似误点的制作台。
- 其余情况允许保存，不用比例缩放或猜测坐标。

该规则只拦截明显跨台误点，不要求四个制作台具有固定排列。

## 数据与接口变化

- Rust `LoginRunStatus` 增加 `Stopping`，serde 输出 `stopping`。
- TypeScript `LoginRunStatus` 增加 `"stopping"`。
- 不新增持久化字段。
- 不新增 Tauri command。
- `special-ops://run-changed` payload 结构不变，仅增加一个枚举值。
- 模板等待超时信息通过现有失败 message 返回。

## 错误处理

- 模板超时：结束当前制作试运行，不点击下一步，不更新制作完成时间。
- 取消发生在任何键鼠输入之后：保留现有“状态不确定”规则。
- 校准/测试与 active run 冲突：立即报“特勤处试运行尚未完成清理”，不排队等待锁。
- 制作已经开始但持久化失败：释放运行资源，最终状态标为失败并明确要求人工确认制作时间；不得自动重跑或伪报成功。内存 settings 采用 copy-on-write，磁盘保存失败时不得留下半更新状态。
- 点击点跨台：拒绝提交新坐标，保留旧坐标。

## 测试

### Rust

- 制作成功持久化返回新 revision，测试必须在有界时间内完成。
- closure 内不再调用 `current_revision()` 的结构回归测试。
- 单目标和多目标等待在 30 秒 deadline 后返回最后 similarity。
- 取消优先于超时。
- `craft.abort` 只消费一组双采样并记录第二次采样时间。
- 普通取消、紧急停止均经历 `stopping -> stopped -> active cleared`。
- worker 与停止请求只执行一次持久化、一次资源清理。
- active run 时保存、测试和框选 command 快速失败。
- 制作台点击点落入其他制作台包络时拒绝，正确区域允许。

### 前端

- `stopping` 状态继续禁用启动、编辑、框选和测试。
- final snapshot 后必须等 bootstrap 的 `runSnapshot: null` 才开放操作。
- 制作等待阶段显示对应步骤文案。
- 超时信息展示目标 key 与 similarity。
