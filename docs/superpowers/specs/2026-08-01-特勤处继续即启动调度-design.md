# 特勤处“继续”即启动调度设计

## 状态

调度规则已实现；桌面实机发现“继续”触发到期轮次时存在 Tauri 主线程死锁，修正设计已批准、待实现。

## 问题

当前“继续”通过 `special_ops_set_paused(false)` 解除暂停，但随后调用 `resume_without_launch()`，实际会把 scheduler 设为未 armed。结果是：页面虽然显示继续状态，未来任务到期也可能不执行。普通设置保存又会在启用且未暂停时 arm scheduler，导致是否自动执行取决于继续后是否发生配置保存，行为不可预测。

## 方案裁决

采用“继续即 arm”方案：

1. 用户点击“继续”并成功持久化 `paused = false` 后，立即 arm scheduler。
2. 当前存在逾期制作或当天待兑换子弹时，scheduler 立即创建多账号 round。
3. 当前只有未来任务时，scheduler 保持 armed，等待任务计划时间后创建 round。
4. 应用启动仍强制暂停并保持 scheduler 未 armed；打开应用不得自动接管键鼠。
5. 点击“暂停”立即 disarm；active round 中点击暂停继续沿用“当前账号完成后暂停”规则。
6. “开始当前到期轮次”按钮保留，作为用户主动立即触发现有到期任务的入口；它不承担启用后台调度的唯一职责。
7. 启用且未暂停时保存配置继续保持 scheduler armed，语义与“继续”一致，不再构成隐藏触发路径。

未采用方案：

- 继续只解除暂停、另增“启动调度”按钮：状态重复，用户无法从“继续”判断是否会到点执行。
- 新增持久化 `armed` 字段：应用启动必须强制暂停，armed 不应跨重启恢复；新增 schema 无收益。
- 删除“开始当前到期轮次”：仍需保留明确的手动立即触发和测试入口。

## 状态转换

| 用户或系统动作 | `paused` | scheduler | 后续行为 |
|---|---:|---|---|
| 应用启动 | `true` | disarmed | 仅恢复并显示任务，不自动执行 |
| 点击继续成功 | `false` | armed | 逾期任务立即执行；未来任务等待到点 |
| 点击暂停 | `true` | disarmed | 不启动新账号或新 round |
| active round 中请求暂停 | round 完成当前账号后持久化暂停 | 完成后 disarmed | 不切换下一账号 |
| 休眠或时间跳变超过 60 秒 | `true` | disarmed | 汇总逾期任务，等待再次点击继续 |
| scheduler 启动 round 失败 | `true` | disarmed | 沿用现有全局暂停与错误记录 |
| 继续状态下保存配置 | `false` | armed | 按新计划重新计算并等待或执行 |

## 实现范围

- 将 `RoundScheduler::resume_without_launch()` 改为表达真实语义的 `resume()`，内部调用 `arm()`。
- `special_ops_set_paused(false)` 调用 `resume()`；暂停分支继续调用 `disarm()`。
- 不增加持久化字段、Tauri command、事件、按钮或 runtime 状态。
- 不修改 `build_schedule()`、任务合并、账号排序、制作/子弹执行顺序、暂停边界或紧急停止。

## 并发与错误边界

- `special_ops_set_paused` 必须先完成 `paused = false` 的持久化，再 arm scheduler，避免 worker 读取旧暂停状态。
- scheduler 已 armed 时重复 arm 幂等，只更新原子状态并唤醒 worker。
- active run 仍由 scheduler 的 `active_run` 检查阻止重复启动。
- 用户点击继续后若 preflight 或 round 冻结失败，沿用现有 `launch_due_round` 失败路径：disarm、持久化全局暂停并报告错误。

### “继续”启动轮次的主线程边界

实机日志确认：同步 Tauri command `special_ops_set_paused` 在主线程完成持久化并 arm scheduler 后，scheduler worker 立即进入到期轮次启动。worker 随后调用 Tauri 同步窗口 getter `main.is_visible()`；该 getter 向主事件循环发送消息并等待响应，而主线程仍在完成原 command 的 IPC 响应，形成互等。

修正规则：

- 将 `special_ops_set_paused` 改为 async Tauri command，使 command 主体由 Tauri async runtime 执行，不占用主事件循环。
- 保持“持久化 `paused = false` 后再 arm”顺序不变。
- 不延迟到期任务、不跳过窗口预检、不拆分前端 command，也不增加固定等待。
- 不修改 scheduler、round、窗口隐藏、操作提示窗或业务状态机。
- 保留启动边界日志用于实机回归；删除仅用于逐窗口定位的临时细分日志。

## 测试

Rust 单元测试至少覆盖：

1. scheduler 未 armed 时，即使任务已到期也不启动。
2. 调用 `resume()` 后，已到期任务立即启动。
3. 调用 `resume()` 后，未来任务到期前不启动，到期后启动。
4. 调用 `disarm()` 后不启动新 round。
5. active run 继续阻止重复启动。
6. 晚醒超过 60 秒继续暂停而非自动执行。
7. `special_ops_set_paused` 保持 async Tauri command，防止同步 command 再次占用主事件循环后唤醒 scheduler。

桌面回归：点击一次“继续”，command 正常返回；存在逾期任务时立即创建 round，主窗口保持响应，操作提示窗正常出现。
