# 特勤处配置纳入 Profile 备份 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with checkpoints.

**Goal:** 将 `SpecialOpsSettings` 纳入现有 Profile 保存、导入、导出和切换流程，并保证运行中的特勤处不会被切换配置打断。

**Status:** 已实现并完成验证；复选框保留为实施轨迹。

**Architecture:** 扩展 `ToolSettingsSnapshot` 增加 `Option<SpecialOpsSettings>`，沿用 Profile 现有快照序列化和 apply 入口。Profile apply 先预校验特勤处快照，再在既有 `SettingsCoordinator`/apply lock 内停止或拒绝特勤处运行、写入并 reload 特勤处设置；应用成功后显式 disarm scheduler、暂停设置并失效利润查询 runtime。特勤处常规保存通过受控同步 helper 更新激活 Profile 快照，避免 Profile apply 期间把目标快照又写回旧 Profile。

**Tech Stack:** Rust、Tauri 2、Serde、现有 `SettingsCoordinator`、Vitest/Rust tests。

- [ ] **Step 3: 实现特勤处 apply helper**

在 `special_ops::SpecialOpsState` 增加：

```rust
pub(crate) fn ensure_profile_apply_allowed(&self) -> Result<(), String>;
pub(crate) fn apply_profile_settings(
    &self,
    app: &AppHandle,
    settings: SpecialOpsSettings,
    revision: u64,
) -> Result<(), String>;
pub(crate) fn settings_snapshot(&self) -> Result<SpecialOpsSettings, String>;
```

`ensure_profile_apply_allowed` 检查 `login_runtime.snapshot()`；存在试运行或轮次时返回中文错误，不发送 stop/emergency 输入。

`apply_profile_settings` 先调用 `normalize_settings`，写入 `special_ops_settings.json`，成功后替换内存 settings；随后：

```rust
self.round_scheduler.disarm();
self.profit_runtime.invalidate("Profile 已切换，利润查询已取消");
```

将 `paused` 固定为 `true` 后再保存一次，最后由 Profile apply 调用现有 `emit_state`。应用旧 Profile（`None`）直接跳过。

- [ ] **Step 4: 把特勤处接入 `apply_snapshot_to_tools`**

在 `apply.rs`：

1. 读取 `snapshot.special_ops.as_ref()` 并 normalize，确保 normalize 失败发生在既有五工具写盘前。
2. 若存在 `SpecialOpsState`，调用 `ensure_profile_apply_allowed`。
3. 保留当前五工具停止/写盘/reload 顺序。
4. 五工具 apply 成功后调用 `apply_profile_settings`；没有 `specialOps` 时不触碰当前特勤处配置。

特勤处写盘失败返回错误，不替换其内存 settings，不更新 active Profile；不额外实现跨六个文件事务，保持现有 Profile apply 语义。

测试 active Profile 存在时，SpecialOps 配置更新后快照字段和 `updated_at` 更新；无 active Profile 时只保存特勤处设置、不创建 Profile。

- [ ] **Step 2: 在 `ActiveProfileSnapshotPatch` 添加特勤处分支**

加入：

```rust

```

匹配时写入 `profile.snapshot.special_ops = Some(value)`。

- [ ] **Step 3: 防止 Profile apply 期间反向同步**

在 `ProfileState` 增加进程内 apply guard（沿用 `apply_lock` 生命周期），并暴露 `profile::is_applying(app)`；特勤处统一保存 helper 在该 guard 为真时只写 `special_ops_settings.json`，不更新 active Profile snapshot。

- [ ] **Step 4: 接入特勤处统一保存路径**

在 `special_ops::save_settings` 成功写盘后，若 `profile::is_applying(app)` 为假，则调用：

```rust
crate::profile::update_active_profile_snapshot(
    app,
    crate::profile::ActiveProfileSnapshotPatch::SpecialOps(Box::new(settings.clone())),
)?;
```

保持现有调用点不变，避免遗漏制作时间、人工校正、利润审计等持久化路径。Profile apply 期间由 guard 阻止该回写。

- [ ] **Step 5: 验证导入不自动应用**

保留 `profile_import`/`profile_import_from_path` 只加入 Profile 列表；增加测试确认 active Profile ID 不变，特勤处文件和内存不变，直到显式 `profile_apply`。
